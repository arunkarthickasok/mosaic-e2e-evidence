Mosaic 1.0 — authoring UI/UX

The complete design: token sheet, component inventory and every screen at desktop, tablet and mobile. Open any file below straight from the repository.

Foundations

  • tokens/tokens.css — the compiled custom properties, light and dark
  • tokens/tokens.json — the source of truth, with a usage note on every token
  • src/mosaic-ui.css — the builder’s stylesheet, tokens only
  • components/index.html — the component inventory

Screens

  • 1. Builder inside the node form
    1440 · 1024 · 390
    The builder is a field, so it stays inside the form: Drupal keeps its title, sidebar and Save, and Mosaic claims one bordered rectangle with its own tokens — no takeover, no second Save button competing with Drupal’s.
  • 2. The same component, edited on the live page
    1440 · 1024 · 390
    The dialog is docked, not centred, so the component being edited stays visible beside it — and it renders the identical rail sections, because two implementations of one panel is how the two surfaces drift apart.
  • 3. Five slots, and a library that owns the look
    1440 · 1024
    Each slot states its own rules on the canvas, the required one is marked rather than silently refused, and Style/Spacing/Responsive are gone from the rail — replaced by one sentence naming who owns the styling instead of greyed-out controls that imply a permission problem.
  • 4. A slot bound to a View
    1440 · 390
    Binding is shown as a chain an author can read end to end — View, display, which page field feeds the argument, what each row becomes, which field lands where — and the empty and failing states sit on the same screen, because those are the two an author never sees until production.
  • 5. Component libraries
    1440 · 1024
    Readiness is never a bare badge: every Attention and Blocked carries the field and the reason, and the schema-derived fields and slots are printed as living documentation, so the page cannot go stale relative to the code.
  • 6. Content-type governance
    1440 · 390
    The library switch and the per-component picks sit on one form because they are one decision, and the sentence that defines Restricted is next to the control rather than in a help page nobody opens.
  • 7. Empty states
    1440
    Five designed nothings. The one that earns the most care is “library missing”: it prints the stored values in full and says they are kept, because an author who cannot see their content assumes it is gone and deletes the component.
  • 8. Keyboard move, and the errors that stop a save
    1440
    Move mode is explicit, announced and reversible with Esc; both save errors lead with an alert the author is moved into, and both are written in the author’s language — “Teaser (Olivero) needs content in its Content area”, never a machine name or “validation failed”.
  • 9. Light, dark, Claro and Gin
    1440
    Four surroundings, one builder. Light and dark both resolve from tokens.json, and the Claro and Gin frames prove the point the other way round: the chrome changes completely and not one pixel inside the border moves.
